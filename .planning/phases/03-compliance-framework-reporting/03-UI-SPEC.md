# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** a compliance-framework labeling **layer** on top of two existing
pages — `templates/scan_report.html` (COMP-01/COMP-02: per-finding OWASP/ASVS tags + a
compliance-grouped/filterable view, alongside the existing severity-grouped view) and
`templates/asset_detail.html` (COMP-03: a new "Compliance coverage" summary section). No new
page/route is introduced. This phase adds **zero new visual language** beyond one new neutral pill
variant and one new lightweight toggle control — every other element reuses `.card`, `.pill`,
`.badge`, `.status-pill`, `.finding`, `.details`/`.summary` accordion, `.table-scroll`, `.warn-box`,
and the `<code>`/`Fira Code` conventions already established in `base.html` and extended by Phase 1
(`asset_detail.html`) and Phase 2 (`api_tokens.html`).

This is a **read-only reporting feature**: it introduces no new form, no new destructive action, and
no new primary conversion CTA. The design contract below is proportionately lighter on
Copywriting/Color than Phase 1/2's contracts for that reason.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — server-rendered Flask/Jinja2 app (no `package.json`/`components.json`/React/Next/Vite project in the repo). The shadcn initialization gate is **not applicable**, same finding as Phase 1 and Phase 2's UI-SPECs. |
| Preset | not applicable |
| Component library | none — hand-rolled CSS in `templates/base.html` plus page-scoped `<style>` blocks (`scan_report.html`'s own `<style>` block already exists; `asset_detail.html`'s own `<style>` block already exists — both extended, not replaced, by this phase). Reuse existing classes (`.card`, `.pill`, `.badge`, `.status-pill`, `.finding`, `details`/`summary`, `.table-scroll`, `.note`, `.empty`, `.warn-box`) rather than inventing parallel ones. |
| Icon library | none (npm) — hand-authored inline `<symbol>` SVG sprite in `base.html`. This phase adds **no new icon symbol** — the compliance pill is a text-only tag (OWASP category strings are already self-explanatory, e.g. "A03:2021-Injection"; an icon would add noise without adding information, unlike Phase 1's schedule/pause/resume icons which replaced otherwise-ambiguous actions). |
| Font | Fira Sans (UI/body/headings), Fira Code (mono — OWASP/ASVS code strings, e.g. `A03:2021`, `V5.3`, read as identifiers/codes exactly like existing hostname/header-value mono treatment). Both already loaded in `base.html`; no new font. |

### Primary visual anchor per surface touched

- **`scan_report.html`'s Findings section:** unchanged — the existing severity pills/score gauge
  remain the primary anchor. The new grouping toggle is a **secondary, low-emphasis control**
  (styled with `.btn.ghost`/`.btn.secondary`, never accent) placed directly above the `Findings (N)`
  heading — it must not visually compete with the score gauge or severity pills for attention.
- **`asset_detail.html`'s new "Compliance coverage" section:** a plain `.card` list, styled at the
  same visual weight as the existing "Scan history" table card — not elevated above the risk-score
  gauge/trend chart, which remain this page's established primary anchor (per Phase 1's UI-SPEC).

## Spacing Scale

Declared/used values for this phase's new markup — standard 8pt scale only, reused verbatim from
Phase 1/2's already-declared scale, no new values introduced:

| Token | Value | Usage |
|-------|-------|-------|
| `--space-1` | 4px | Gap between the compliance pill and its optional ASVS caption text on a finding card |
| `--space-2` | 8px | Gap between the two grouping-toggle links; gap between compliance-coverage row's label and status pill |
| `--space-4` | 16px | Compliance-coverage summary row internal padding; vertical rhythm between rows |
| `--space-5` | 24px | `.card` outer padding for the new "Compliance coverage" section, matching every other `.card` on this page |
| `--space-6` | 32px | `h2.section` top margin above "Compliance coverage", matching the existing section-spacing rhythm |

This phase introduces **zero new spacing values**.

Cell/control padding used by this phase's new markup — 4px-multiple values, consistent with the
scale above (no exceptions needed):

- The compliance-coverage summary rows use `8px 8px` cell padding (if rendered as a `<table>`,
  i.e. `--space-2` in both directions) or the `.finding` block's existing
  `padding: var(--space-4) var(--space-4)` (16px 16px, if rendered as stacked cards) — planner's
  choice between the two existing list-rendering patterns already in this codebase (see UI
  Considerations below).
- The grouping-toggle links use `8px 12px` padding (`--space-2` vertical, 12px horizontal — both
  4px multiples).

No icon-only controls are introduced this phase, so the 44px-minimum-touch-target exception from
Phase 1 does not apply here.

## Typography

This phase declares its own type roles below — the sizes/weights genuinely authored by this
phase's new markup. No new `font-size` or `font-weight` value is introduced; every value below
already exists in `base.html`'s (and Phase 1/2's) type system.

**This phase declares (new-role text this phase authors):**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 13.5px | 600 (semibold) | 1.3 |

Exactly two weights, 400 and 600, cover every piece of genuinely new text this phase writes:
- **Body** (16/400/1.5): the "not enough data yet" hint paragraph on the Compliance coverage
  section (reusing `.sparkline-card .hint`'s exact styling from Phase 1).
- **Label** (13.5/600/1.3): compliance-coverage row category names, and the grouping-toggle link
  text — set to exactly 13.5px (overriding the `.btn`/link-button convention's native 14.5px for
  this specific control), so it collapses fully into the Label role declared above instead of
  introducing a distinct fifth size.

**Inherited (unchanged, pre-existing, out of scope for this phase — this phase places new markup
using these existing sizes, it does not (re)define them):**

| Role | Size | Weight | Line Height | Where it appears in this phase's surfaces |
|------|------|--------|-------------|--------------------------------------------|
| Pill/caption | 11.5px | 700 (bold — pre-existing `.pill` token) | normal | The new `.pill.compliance` OWASP-category tag reuses `.pill`'s exact existing font rules unchanged (`font-size:11.5px; font-weight:700; text-transform:uppercase`, etc. — see `base.html:60`). The optional ASVS caption text (e.g. `ASVS V5.3`) is rendered at the same 11.5px in `Fira Code`/`--muted`, unbolded — matching the existing `.finding .cat` caption-text convention (`base.html:99`), not a new size. |
| Heading | 24px | 700 (bold — pre-existing `h1` token) | 1.2 | Unaffected — this phase adds no new `<h1>`. |

> **Note for gsd-ui-checker:** per Phase 1's already-confirmed, project-level typography exception
> (force-approved 2026-08-10, referenced again in Phase 2's UI-SPEC), inherited pill/caption sizing
> below 13.5px is pre-existing house convention, not a new phase-invented size — please evaluate

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#020617` (`--bg`) | Page background — unchanged |
| Secondary (30%) | `#0b1220` → `#0f172a` gradient (`--panel`/`--panel2`), `#1e293b` (`--border`) | `.card` background for the new "Compliance coverage" section; `.finding`/table row backgrounds for compliance-grouped findings (unchanged from severity-grouped findings) |
| Accent (10%) | `#22c55e` (`--accent`) | **Not introduced or expanded by this phase.** No new accent-colored element exists in this phase's scope — see below. |
| Destructive | `#f87171` (`--critical`, reused) | **Not used by this phase.** No destructive action exists in this phase's scope (pure read-only reporting). |

**Accent reserved for (unchanged from the pre-existing whole-app list — this phase adds nothing to
it):** primary CTAs, links, `.status-pill.completed`/`.pill.pass`, focus ring, the risk-score
gauge's high-score arc. The grouping toggle's **active** state must **not** use accent — see below.

**New, this phase (one addition — a neutral, non-severity, non-accent color for the compliance
tag):**
- `.pill.compliance` — background `rgba(139,150,173,.14)`, text `var(--muted)` (`#8b96ad`). Same
  rgba-background-plus-solid-text-color *formula* every other `.pill` variant already uses
  (`base.html:61-66`), applied to the one existing neutral token (`--muted`) rather than inventing a
  new hex value. Chosen over `--telemetry` (the "in-progress" blue) per RESEARCH.md's Open
  Questions recommendation: `--telemetry` already carries an "in progress/live" meaning on this
  page's live-scan feed and dashboard; reusing it for a static compliance tag would misapply that
  semantic. `--muted` carries no competing meaning and is the lowest-risk choice.
- **Reused, not new — grouping-toggle "active" state:** `.btn.secondary` (bordered, `var(--text)`
  on `var(--panel)`) for the active toggle option, `.btn.ghost` (transparent, `var(--muted)`) for
  the inactive option. Matches Phase 1's explicit precedent that a *view/mode* toggle (not a
  conversion action) must not be accent-colored — "Pause"/"Resume" schedule buttons established this
  exact rule already.
- **Reused, not new — compliance-coverage row status pills:** reuse the existing severity pill
  system (`.pill.critical`/`.high`/`.medium`/`.low`/`.info`/`.pass`) to show a category's worst
  finding severity ("Failing" state), and a **new muted "not checked" state** using the exact same
  `.finding.locked-card`/`.badge` opacity-.65-plus-`--muted` treatment Phase 1 already established
  for tier-locked checks (`scan_report.html:35-36`) — not a new visual pattern, the same
  "locked/unavailable" language reused for "not yet checked."

**Destructive reserved for:** not applicable this phase — no destructive action exists.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **None.** This phase adds no new form, no new create/generate/submit action — it is a read-only labeling and grouping layer on existing report/asset pages. |
| Grouping toggle — label pair | **"Group by:"** followed by two toggle options: **"Severity"** (default — preserves current behavior exactly) and **"Compliance"**. Matches this app's existing terse, lowercase-except-labels UI copy style (`h2.section` labels like "Detailed check output"). |
| Compliance pill (per finding) | The check's mapped OWASP Top 10 category string verbatim, e.g. **"A03:2021-Injection"** — sourced directly from `CHECK_COMPLIANCE[f.check_name]["owasp"]`, not a paraphrase, so the label an auditor sees matches the official OWASP naming exactly. |
| Compliance pill — unmapped fallback (D-04) | **"Uncategorized"** — exact string per D-04's explicit instruction, styled identically to every other `.pill.compliance` (not a warning/error color — an unmapped finding is not itself a problem). |
| ASVS caption (optional, per D-01) | `ASVS {ref}`, e.g. **"ASVS V5.3"** — rendered only when `CHECK_COMPLIANCE[...]["asvs"]` is non-null; omitted entirely (no "N/A" placeholder) when absent, since D-01 makes ASVS optional per-check, not a required-but-sometimes-empty field. |
| Compliance-coverage section heading | **"Compliance coverage"** (`h2.section`, matches the existing "Risk score over time"/"Schedule"/"Scan history" heading style exactly) |
| Compliance-coverage row — status: passing | **"Passing"** — `.pill.pass`, shown when the category's checks ran on the most-recent completed scan of that scan type and found no findings |
| Compliance-coverage row — status: failing | **"{N} finding(s), highest: {severity}"** — e.g. "3 findings, highest: high" — uses the existing severity pill color for `{severity}`, not a new color |
| Compliance-coverage row — status: not checked | **"Not checked"** — muted/locked-style badge, reusing `locked_card`'s existing tone; if the reason is tier-locking specifically, append `scan_report.html`'s existing locked-check upgrade copy verbatim ("Requires the **{tier}** plan... [Upgrade](url)") rather than writing new upgrade copy |
| Empty state — no compliance data yet | **Reused verbatim from `asset_detail.html`'s existing scan-history empty card:** "This Asset hasn't been scanned yet..." — the "Compliance coverage" section is **omitted entirely** (not rendered as a second, redundant empty box) until at least one completed scan exists for this Asset. See UI Considerations below. |
| Empty state — scans exist but none completed yet | **"Not enough completed scans yet to show compliance coverage."** — new copy, but matching the exact tone/length of the existing sparkline card's "Not enough completed scans yet for a trend line." (Phase 1, `asset_detail.html`), styled identically (`.hint`, `--muted`, no icon). |
| Error state | **None new.** No new error condition is user-facing this phase — a missing/corrupt report JSON while aggregating coverage is silently skipped (matches the existing "never let one check's failure break the page" convention in `CLAUDE.md`), and an unrecognized `?group=` query value silently falls back to the default "Severity" grouping rather than showing an error. |
| Destructive confirmation | **Not applicable.** No destructive action exists in this phase's scope. |

## UI Considerations

Applicable state considerations resolved: **16 covered, 3 backstop, 0 unresolved**

Elements this phase introduces (classified against the 8-category taxonomy; only categories whose
`applies to element kinds` intersect the element's kind are raised):

- **E1 — Severity/Compliance grouping toggle** (`interactive-control`) on `scan_report.html`
- **E2 — Inline compliance pill (+ optional ASVS caption)** (`static-content`) on every finding
  card, both grouping modes
- **E3 — "Uncategorized" bucket** (`static-content`) — a category header within the
  compliance-grouped view for findings with no `CHECK_COMPLIANCE` mapping
- **E4 — Compliance coverage summary** (`list-collection`) on `asset_detail.html`

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | E1 | ✅ covered | Toggle is only rendered when `r.findings` is non-empty — matches the existing `{% else %}<p class="empty">No findings.</p>{% endfor %}` branch already on this page; no point toggling the grouping of zero items, and rendering it anyway would be a dead control |
| empty | E4 (asset never scanned) | ✅ covered | Section omitted entirely; the page's existing "This Asset hasn't been scanned yet..." card (Phase 1) already covers this state — no duplicate/second empty box, per Copywriting Contract above |
| empty | E4 (scans exist, none completed) | ✅ covered | New copy defined in Copywriting Contract, styled identically to the existing sparkline card's equivalent empty state |
| empty | E3 (no unmapped findings on this scan) | ✅ covered | The "Uncategorized" bucket simply does not render — same `{% if f.category != ns.current_cat %}` branch pattern the existing severity loop already uses for categories with zero members, not a new mechanism |
| loading | E1, E4 | ✅ covered | Not applicable — full server-rendered GET page load, no client-side async fetch; consistent with every other page in this app having no loading state (Phase 1/2 precedent) |
| error | E1 (unrecognized `?group=` value) | ✅ covered | Silent fallback to default "Severity" grouping, defined in Copywriting Contract — matches this codebase's established "missing dict entry degrades gracefully" convention (`CHECK_LABELS`'s title-cased fallback, `CHECK_CATEGORY`'s `"shield"` fallback) |
| error | E4 (one scan's report JSON fails to load during aggregation) | 🧪 backstop | Skip that scan's contribution silently and continue aggregating the rest, per Copywriting Contract's error-state row — flagged for explicit verification since this is a new read-multiple-files-and-continue-on-failure code path, not previously exercised elsewhere in this exact shape |
| populated | E1 | ✅ covered | "Compliance" mode groups findings by `CHECK_COMPLIANCE[f.check_name]["owasp"]` (Uncategorized fallback) using the **exact same** `<details>`/`<summary>`/`namespace`-tracked accordion markup the existing severity loop already uses (`scan_report.html:111-132`) — a parallel loop with a different grouping key, not new markup |
| populated | E2 | ✅ covered | Rendered on every finding card in both grouping modes — visible even when the page is in "Severity" mode, satisfying COMP-02's "not only by severity" requirement without requiring the user to switch modes to see the mapping at all |
| populated | E4 | ✅ covered | One row per OWASP category present in `CHECK_COMPLIANCE` and relevant to scan types this Asset has completed at least once; status per Copywriting Contract's three-state row (Passing/Failing/Not checked); "most-recent completed scan of each scan_type" semantics per RESEARCH.md's Pitfall 3 recommendation — **this choice is user-visible; the plan must state it explicitly on the page or in an adjacent hint, e.g. "as of the most recent scan"** |
| partial | E4 (some categories checked, some never run — free-tier Asset, only base scans configured) | ✅ covered | "Not checked" muted/locked status per Copywriting Contract, not silently omitted from the list — mirrors D-04's "explicit bucket rather than silently dropped" philosophy generalized from findings to categories |
| partial | E1/E2 (a finding whose check has an OWASP tag but no ASVS ref) | ✅ covered | ASVS caption simply omitted (no placeholder text) per Copywriting Contract — D-01 makes it genuinely optional, not a required-but-empty field |
| overflow | E2 (pill + caption on a narrow viewport) | 🧪 backstop | `.pill.compliance` and the ASVS caption sit inline after the existing severity `.badge`, wrapping onto a second line via normal inline-flex wrap if the finding card is too narrow — reuses the `.finding`'s existing flex-wrap-tolerant layout, but this is a new inline-element combination not previously exercised on this card, flagged for a narrow-viewport visual check |
| overflow | E4 (long "highest severity" or category text) | ✅ covered | OWASP category strings and severity words are short, fixed, dictionary-sourced values (not user input) — no truncation logic needed, matching the low-risk framing RESEARCH.md's Assumptions Log already gives these strings |
| overflow | E1 | ✅ covered | Two short fixed-length labels ("Severity"/"Compliance"), no overflow risk at any viewport |
| zero-one-many | E3 | ✅ covered | Zero unmapped findings → bucket doesn't render (above); one/many → same accordion markup, no singular/plural copy variance needed (matches the existing severity-category loop having none either) |
| zero-one-many | E4 | 🧪 backstop | The "zero mapped categories relevant to this Asset" case should be unreachable given COMP-04's regression test guarantees every dispatchable check name has a `CHECK_COMPLIANCE` entry — flagged as a backstop rather than assumed-impossible, since it depends on that regression test actually running in CI, not on this UI-SPEC alone |
| long-text | E2, E4 | ✅ covered | All new text this phase renders (OWASP/ASVS strings, "Passing"/"Failing"/"Not checked") is short and dictionary-sourced, not free-form/user-controlled — no long-text risk exists comparable to Phase 1/2's hostname/token-name concerns |
