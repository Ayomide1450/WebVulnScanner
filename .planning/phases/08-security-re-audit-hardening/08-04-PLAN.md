<objective>
Close SEC-03: the one confirmed-open vulnerability this phase found.

`is_ssrf_safe_hostname()` runs once, at submission time, in `scan_routes._unsafe_target_error`. But
the `requests.Session` every check function shares - built by `checks._mk_session()` at
`checks.py:361-364` - is a plain, unmodified `requests.Session()`. Most of the 33 request call
sites in `checks.py` either omit `allow_redirects` (requests defaults it to `True`) or pass it
explicitly, so a target that resolves to a public address at submission and then 302s to
`127.0.0.1`, `169.254.169.254`, or an RFC1918 host is followed with no re-check at all. An attacker
who controls a public hostname they legitimately own gets the scanner to fetch the hosting network's
internals for them.

This is the phase's one required production code change (D-03: fix it immediately, record it plainly).
It is a single-point fix: subclass `requests.Session`, override `resolve_redirects` to re-validate
each hop's hostname through the existing `is_ssrf_safe_hostname()`, and return that subclass from
`_mk_session()`. Every check inherits it; no call site changes.

Purpose: SEC-03 is the only requirement in this phase where the code is actually wrong rather than
merely untested.
Output: `_SSRFSafeSession` in `checks.py`, a redirect-following test suite in
`tests/test_ssrf_guard.py`, and an orchestrator session-construction lock in
`tests/test_scan_engine.py`.
</objective>
