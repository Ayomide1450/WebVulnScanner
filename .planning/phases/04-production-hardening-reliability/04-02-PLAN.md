<objective>
Make the app's rate limits correct under more than one gunicorn worker by proving the already-wired
`RATELIMIT_STORAGE_URI` path actually shares counters across independent limiter instances, and by
shipping the Redis client that path needs (HARD-01, D-01).

Purpose: `/login`, `/signup`, the invoice endpoints and Phase 2's API-token endpoints all rely on
Flask-Limiter, whose default in-memory storage lives inside a single process. With two workers,
each worker enforces its own private counter and the effective limit silently doubles. The config
key to fix that already exists and is read by nobody's test — this plan turns "there is a config
value" into "there is a proof."

Output: `redis` in `requirements.txt`, `fakeredis` in `requirements-dev.txt`, a new
`tests/test_ratelimit_storage.py`, a corrected comment on the `limiter` singleton, and a boot-time
log line naming the backend actually in use.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted client -> rate-limited endpoints | `/login`, `/signup`, invoice create/verify, and the Phase 2 API-token endpoints are the surfaces whose limits this plan makes correct under multiple workers. |
| app worker -> rate-limit storage backend | A new outbound dependency when `RATELIMIT_STORAGE_URI` is set: the worker connects to a Redis instance whose URL carries credentials. |
| environment -> app config | `RATELIMIT_STORAGE_URI` arrives from the deploy environment and selects the storage backend at `init_app()` time. |
