<objective>
Finish the org-invite flow so an invited teammate actually lands in the inviting org at the invited
role, bind the invite token to the invited email address so a forwarded link cannot be redeemed by
someone else, and put the previously-untested invite and domain-verification flows under automated
coverage (HARD-03, D-05 through D-08).

Purpose: `org_routes.invite()` has been generating signed links since it was written, and
`/signup` has never read them — `decode_invite_token` has zero call sites in the entire repo, and
the invite email itself admits the gap in its own body text. HARD-03 asks for test coverage of
"invite / role-change / domain-verification flows"; there is no honest way to test an invite flow
that stops at the mailbox, so this plan finishes it first and then covers it.

Output: a 3-argument `generate_invite_token`, an email-checking `decode_invite_token`, an
invite-mode branch in `signup()` with the matching template conditional, corrected copy on the
org-admin page and in the invite email, and two new test modules.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email recipient -> `/signup?invite=` | A signed token travels through an untrusted channel (a mailbox that can be forwarded, leaked, or read by someone else) and, on return, decides which organization and role a brand-new account receives. |
| anonymous browser -> `signup()` | Invite mode changes what an unauthenticated request can cause: joining an existing org rather than only creating one. |
| org admin -> invite form | An admin picks the role the token grants, including the admin role. |
| scanned/verified domain -> `verify_domain` | DNS TXT answers and well-known HTTP responses come from infrastructure the app does not control and are compared against a server-generated token. |
