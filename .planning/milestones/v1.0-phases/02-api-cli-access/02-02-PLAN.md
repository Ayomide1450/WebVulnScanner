## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| CLI/script (Bearer token) &rarr; `POST /api/v1/assets/<id>/scans` | Untrusted request triggers a real outbound network scan against `asset.target_url` - the same trust boundary the web UI's `new_scan_*` routes and the scheduler's tick already cross, now reachable via a third entry point |
| CLI/script (Bearer token) &rarr; `GET /api/v1/scans/<id>/report` | Untrusted request reads another user's/org's potentially-sensitive findings data if ownership scoping is wrong |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-02-07 | Tampering / Elevation of Privilege | `api_routes.py::trigger_scan` | high | mitigate | 100% reuse of `scheduler._fire(asset)` - identical SSRF re-check (`is_ssrf_safe_hostname`) and tier re-check (`entitlements.effective_tier_for_org`) as the scheduler's own fire-time logic; zero new dispatch code |
| T-02-08 | Elevation of Privilege | `api_routes.py::fetch_report` | high | mitigate | `_check_asset_access(scan.asset)` for Asset-linked scans (Pitfall 1 fix, org-shared) vs. `_check_ownership(scan)` for manual scans (creator-or-admin) - branch is explicit and tested both ways |
| T-02-09 | Elevation of Privilege | `api_routes.py::trigger_scan` | high | mitigate | Tier gating comes free via `scheduler._fire`'s existing `entitlements.effective_tier_for_org` re-check - no separate/duplicate tier-check code exists to drift out of sync |
| T-02-10 | Denial of Service | `api_routes.py::trigger_scan` | medium | mitigate | Rate-limited (30/min, tighter than the 60/min read limit) since this route spawns a real outbound scan thread per successful call |
