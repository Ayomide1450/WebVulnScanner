<objective>
Give a scan report a compliance-framework view: findings grouped by their mapped OWASP Top 10
category, reachable from a low-emphasis toggle beside the existing severity grouping, with an
explicit Uncategorized bucket for anything unmapped.

Purpose: COMP-02 — "a scan report includes a compliance-framework view; findings grouped/filterable
by framework category, not only by severity." Plan 03-01 already put the per-finding tag on the
page; this plan makes the report navigable by that tag.

Output: a `group` query-parameter allowlist and a pure grouping helper in `scan_routes.py`, a
`finding_card()` macro plus a second accordion branch in `scan_report.html`, and route-level tests.

**Discretion decision recorded (CONTEXT.md left report grouping UX to the planner):** the two modes
are a `?group=` query parameter on the existing `/scan/<id>/report` route with a link-pair toggle —
not a new route, not a client-side filter. Rationale: this app is server-rendered with no
client-side framework, a query parameter keeps a chosen view shareable/bookmarkable, and 03-UI-SPEC's
Copywriting Contract already fixed the silent-fallback behaviour for an unrecognised value.

**Deliberate deviation from 03-PATTERNS.md:** that document proposed a second Jinja loop using the
existing `namespace`-tracked "did the category change" pattern keyed on a computed
`CHECK_COMPLIANCE` lookup. Jinja's `sort(attribute=...)` cannot sort on a computed key, and that
pattern only works on a pre-sorted list — so the grouping is computed in Python and the template
iterates ready-made groups. The rendered accordion markup is unchanged; only where the sort happens
moves. This also makes the grouping unit-testable without rendering a page.
</objective>
