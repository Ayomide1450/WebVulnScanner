<objective>
Give each Asset a compliance-coverage summary: which OWASP Top 10 categories its scans have
actually checked, and which are currently failing — read straight off the existing scan history,
with no new table, no migration, and no new route.

Purpose: COMP-03 — "user can view a per-Asset compliance-coverage summary across its scan history
(which framework categories have been checked, and which are currently failing)."

Output: `summarize_compliance()` and `compliance_coverage()` in `asset_routes.py`, a "Compliance
coverage" card on `asset_detail.html`, and tests in `tests/test_asset_routes.py`.

**Discretion decisions recorded (CONTEXT.md left both to the planner and asked that they be
documented because they are user-visible):**

1. *Placement* — a section on the existing `asset_detail.html`, not a new page or route. It sits
   directly after "Risk score over time" and before "Schedule", so the page reads gauge -> trend ->
   coverage (reporting) and then schedule -> history (administration). Same `.card` weight as the
   Scan history card, never elevated above the risk-score gauge (03-UI-SPEC Design System).
2. *"Currently failing" semantics* — the most recent **completed** scan of each `scan_type` the
   Asset has run, not any-scan-in-history. Rationale: `asset_detail.html`'s existing "Latest scan"
   card and risk-score sparkline already establish "the latest scan is this Asset's current state";
   an any-scan-ever-failing flag would keep showing a category as failing after a real fix landed
   and a later scan came back clean. The page states this scope in visible copy.

**Correction to 03-RESEARCH.md, load-bearing for this plan.** RESEARCH.md states that applying the
mapping at read time means "every already-completed scan report written before this phase ships gets
compliance tags for free, with no backfill". That is true for the *mapping table* but false for
`check_name`, which is scan-time data written into the report JSON by plan 03-01's orchestrator
tagging. A report written before this phase has no `check_name` on any finding, so its findings
cannot be attributed to a category. Counting such a scan's categories as "Passing" because no
finding maps to them would overstate the Asset's posture — exactly the failure this plan's
prohibition forbids. The rule below therefore excludes untaggable reports from the tally instead of
treating them as clean.
</objective>
