<objective>
Ship the guided scan-launch flow end-to-end for one scan type: Select Domain (Step 1) ->
Select Type (Step 2) -> Confirm Authorization + Start Scan (Step 3, Standard Scan) -> a
running scan. This is the tracer slice — it wires every layer this phase touches (route
helpers, a new step-2 route, a shared stepper partial, three templates, the shared CSS
partial, and the test module) on a single working path before the other three scan types
expand out from it in plan 05-02.

Purpose: `/scan/new` today is a flat 4-card chooser that dead-ends into four disconnected
single-form pages, each starting from an empty free-text field even though the org may
already have server-verified domains on file. This plan replaces that entry point with the
linear sequence SCANUX-01 specifies and makes the org's verified domains a first-class,
one-click target source (SCANUX-02) without removing free-text entry (D-01).

Output: a working `/scan/new` -> `/scan/new/type` -> `/scan/new/base` wizard, the shared
`_scan_wizard_stepper.html` partial and step CSS the other three types reuse in 05-02, and
`tests/test_scan_wizard.py` covering it.
</objective>

Decisions implemented by this task — D-01: the verified-domain dropdown is populated from
org-scoped `DomainVerification` rows only (never `Asset` rows) and free-text entry stays an
equally-visible parallel input, never hidden behind a toggle. D-03: the Upgrade-to-Unlock
CTA resolves its destination from whichever gate is actually blocking — `/billing` for a
plan-tier block, `org.verify_domain_view` for a domain-verification block.

Implement in `glassbox/scan_routes.py`, then the templates.

**1. `_verified_domain_choices(user)`** — new helper placed directly above `new_scan`.
Returns a list of domain strings for SCANUX-02's dropdown. Per D-01 it queries
`DomainVerification` only (lazy-import it inside the function, matching the existing
lazy-import convention in `_unsafe_target_error`), filtered on `org_id == user.org_id` and
`verified_at.isnot(None)`, ordered by `domain`. Returns `[]` when `user.org_id` is None.
Docstring must state that `Asset` rows are deliberately not a source because registering an
Asset is not proof of domain ownership (D-01), and that rows with a pending deletion request
are still included because they are still verified.

**2. `_prefill_target(field)`** — new helper. Returns `request.form.get(field, "")` when
`request.method` is `"POST"`, otherwise `request.args.get("target", "")`. The docstring must
explain that the POST branch exists so a validation-error re-render never silently clears
what the user typed (the regression CLAUDE.md records for this page family), and that the
GET branch consumes the `?target=` parameter `scan_report.html`'s re-scan link has emitted
all along but `new_scan_base` previously ignored.

**3. Availability contract constants.** Module-level, above `_tier_flags`:
`AVAILABILITY_INCLUDED = "Included"`, `AVAILABILITY_VERIFIED = "Requires Verified Domain"`,
`AVAILABILITY_PAID = "Requires Paid Plan"` — the three verbatim SCANUX-03 strings. Then a
`SCAN_TYPE_CARDS` tuple of four dicts in the order base, advanced, media, api, each with
keys `key`, `title`, `endpoint`, `cta`, `blurb`. Values:
  - base: title `Standard Scan`, endpoint `scan.new_scan_base`, cta `Run a Standard Scan`,
    blurb copied verbatim from the current `scan_new.html` base card.
  - advanced: title `Advanced / authenticated`, endpoint `scan.new_scan_advanced`, cta
    `Run advanced checks`, blurb copied verbatim from the current advanced card.

    blurb copied verbatim from the current media card.
  - api: title `API exposure scan`, endpoint `scan.new_scan_api`, cta
    `Run API exposure scan`, blurb copied verbatim from the current api card.
Add a comment above the tuple noting the grid is always exactly these four fixed cards
(05-UI-SPEC.md's one unresolved consideration, planned as a fixed assumption) so no
zero/one/many conditional copy is needed.

**4. `_scan_type_availability(tier, org, target_url)`** — new helper returning a list of
four dicts, each being a `SCAN_TYPE_CARDS` entry plus `label`, `unlocked`, `upgrade_url`.
Rules, which implement D-03's context-aware destination:
  - base: always `unlocked=True`, label `AVAILABILITY_INCLUDED`, `upgrade_url=None` (a base
    scan runs on every tier; individual checks inside it are gated by
    `entitlements.allowed_checks`, not by this card).
  - advanced: if `Tier.ORG_VERIFIED <= tier` is false -> label `AVAILABILITY_PAID`,
    `unlocked=False`, `upgrade_url=url_for("billing.view")`. Else if `target_url` is falsy or
    `domain_is_org_verified(org, target_url)` is false -> label `AVAILABILITY_VERIFIED`,
    `unlocked=False`, `upgrade_url=url_for("org.verify_domain_view")`. Else unlocked/Included.
  - media and api: `FEATURE_REQUIREMENTS[key] > tier` -> label `AVAILABILITY_PAID`,
    `unlocked=False`, `upgrade_url=url_for("billing.view")`. Else unlocked/Included.
The docstring must state the blocking-gate precedence explicitly: an insufficient plan tier
is reported first because a plan upgrade is the only thing that can move the user forward;
only once the tier already qualifies does an unverified target domain become the reported
blocker. It must also state, in bold terms, that this helper is **display-only and is not a
gate** — every POST handler keeps its own `FEATURE_REQUIREMENTS`/`authorized*`/
`_unsafe_target_error` checks, which remain the single source of truth, so a hand-crafted
POST to a card rendered as locked is still refused server-side.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `/scan/new`, `/scan/new/type` | `verified_domain` and `target` query parameters are fully attacker-controlled and are both echoed into HTML and used to build links |
| browser -> `/scan/new/base` (POST) | target list, `test_url` and `authorized` come from the form; these reach `normalize_target` and the outbound scan HTTP client |
| Flask -> DB | `_verified_domain_choices` reads `DomainVerification` rows across the whole table and must scope them to the caller's org |
