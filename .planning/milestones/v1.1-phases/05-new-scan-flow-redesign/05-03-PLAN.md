<objective>
Close SCANUX-05 for the three scan types that have no per-check event stream. Base scans
already land on their report automatically via the SSE feed; advanced, media and API scans
open the same long-lived stream but never receive a single event through it, so the page
sits on "Initializing investigation…" and its stale watchdog fires a misleading
"still waiting for an update" message, with no View Report control anywhere.

Purpose: D-04 closes this by adding a lightweight interval poll rather than treating
SCANUX-05 as already satisfied. A dedicated status-only endpoint is chosen over reusing
`/scan/<id>/events` because these three scan types emit no `ScanEvent` rows at all — holding
a long-lived streaming worker connection open per running scan buys nothing here, and a
2-second read of one indexed row is both cheaper on the Fly.io always-on-VM deployment model
and trivially testable. No query logic is duplicated: the endpoint is a `get_or_404` plus
the existing `_check_ownership` guard.

Output: `GET /scan/<id>/status`, a `View Report` control on the progress page for all four
scan types, and a transport branch that leaves base scans on SSE untouched.
</objective>

the raw exception string into a JSON API response would widen the disclosure surface for no
benefit.

Write a docstring covering: why this exists rather than reusing `/scan/<id>/events` (D-04 —
advanced/media/api emit no `ScanEvent` rows, so a long-lived stream costs a worker
connection for nothing and its per-tick event query is dead weight); that it deliberately

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `GET /scan/<id>/status` | `scan_id` is attacker-controlled; the response reveals whether a scan exists and its state |
| browser -> progress page script | the polled JSON drives a `window.location.href` assignment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-11 | Information disclosure | `scan_status()` exposing another org's scan state (IDOR) | high | mitigate | Reuses `_check_ownership`, which aborts 404 (not 403) so a scan id does not confirm its own existence — the same convention `scan_detail`/`scan_events`/`scan_report` already follow. Cross-org, same-org-member and ORG_ADMIN cases are all asserted in Task 1. |
| T-05-12 | Information disclosure | Exception/stack text leaking through the status JSON | medium | mitigate | The payload is exactly two keys, `status` and `report_url`; `error_message` is deliberately not returned, and Task 1's criteria assert a known error string never appears in the response body. |
| T-05-13 | Tampering | `data.report_url` driving `window.location.href` | low | mitigate | The value is produced server-side by `url_for("scan.scan_report", ...)` for a scan the caller already passed `_check_ownership` on — it is never echoed from client input. The client also falls back to a locally-constructed same-origin path when it is null. |
| T-05-14 | Denial of Service | One authenticated request every 2s per open progress page | low | accept | Bounded: polling stops on the first completed/failed tick, only runs for non-base scan types, and each request is one primary-key row read. This strictly replaces a long-lived streaming worker connection that previously did the same work plus a dead per-tick `ScanEvent` query — net load goes down on the Fly.io always-on-VM model. |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no package-manager install task and no new dependency; the package-legitimacy gate does not apply. |
</threat_model>
