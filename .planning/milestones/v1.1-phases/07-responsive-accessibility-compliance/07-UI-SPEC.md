# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is a verify-and-fix responsive/accessibility retrofit of Phase 6's
already-shipped design system (~35 server-rendered Flask/Jinja templates, hand-authored CSS in
`base.html` + 5 shared partials, no build step, no component library). **No new colors, spacing
values, typography sizes, or component shapes are introduced.** Every value below either reuses a
Phase 6 token verbatim or defines a new `@media` breakpoint / interaction-state rule that composes
existing tokens. Where 07-CONTEXT.md (D-01) or 07-RESEARCH.md already answered a design-contract
question, that answer is used directly and marked as pre-populated; the remaining open question
(auth-page mobile fix specifics) is resolved here under **Claude's Discretion** per the `--auto`
mode instructions, since no `checkpoint:human-verify` screenshot review has happened yet.

## Color

**Unchanged from Phase 6 — reused verbatim, no new color introduced.** 07-RESEARCH.md's hand-computed
WCAG luminance math confirms every severity/status text-color token already clears 4.5:1 against
both `--bg` (#020617) and `--panel` (#0b1220) — the tightest case (`--muted` #8b96ad on `--panel`)
computes to ~6.3:1. **Do not redesign the palette.** A11Y-04's actual work is two narrow,
tool-confirmed fixes:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--bg)` #020617 | Page background — unchanged |
| Secondary (30%) | `var(--panel)` #0b1220 → `var(--panel2)` #0f172a | Cards, mobile record-cards (reuse `.card`), form controls — unchanged |
| Accent (10%) | `var(--accent)` #22c55e | Reserved for: `.btn.primary`, links, focus ring, "completed/pass" states — unchanged. Mobile card primary actions reuse `.btn.primary`/`.btn.secondary` exactly as desktop rows do, no new accent usage |
| Destructive | `var(--critical)` #f87171 | Reserved for `.btn.destructive`, `.error-box`, failed states — unchanged. Mobile cards' destructive actions (asset delete, token revoke) keep `.btn.destructive` unchanged |

### A11Y-04 fix 1 — `opacity`-blended disabled/inactive states (contrast risk)

`.btn:disabled { opacity: .5; }` (verified `templates/base.html:81`) and `.pill.not-checked {
opacity: .65; }` (verified `templates/asset_detail.html:24`) blend an otherwise-passing color
toward whatever sits behind them — this is a compositing effect, not a token-value problem, so it
must be verified in its rendered state, not assumed from the base color alone.

**Fix directive (token-based, not a new color):** If a tool-confirmed check (WebAIM Contrast
Checker or DevTools color picker, sampling the actual rendered pixel) shows either opacity state
drops below 4.5:1 against its actual background (`--panel`/`.card` gradient), raise the opacity
value (e.g. `.5` → `.6`, `.65` → `.72`) just enough to clear 4.5:1 — do **not** introduce a new
"disabled" color token. If the tool confirms both already pass, no change is needed; document the
passing ratio in the phase's verification evidence rather than leaving it unconfirmed.

### A11Y-04 fix 2 — `_gauge.html`'s hardcoded (non-token) stroke colors

`_gauge.html`'s SVG gauge stroke is a 4-way hardcoded hex ternary (verified
`templates/_gauge.html:23`): `#34d399` (≥90), `#fbbf24` (≥60), `#fb923c` (≥40), `#fb7185` (<40) —
none of these match `base.html`'s `--pass`/`--medium`/`--high`/`--critical` tokens exactly (e.g.
`#fb7185` vs. token `--critical` #f87171). This is decorative (always paired with the plain-text
score number/grade, so WCAG's non-text-contrast exception for decorative-only color applies), but
was never brought into the token system.

**Fix directive (token-based, not a new color):** Replace the four hardcoded hex literals with
the existing `--pass`/`--medium`/`--high`/`--critical` custom properties (Jinja can't emit
`var(--x)` directly into an SVG `stroke` attribute the same way, so either inline the token's hex
value as a Jinja constant matching `base.html`'s `:root` definition exactly, or move the ternary's
output to a CSS class (`.gauge-fg.pass`/`.medium`/`.high`/`.critical`) that references
`stroke: var(--pass)` etc. in `base.html`, and have `_gauge.html` emit the class name instead of
an inline `stroke=` attribute). Either approach eliminates the drift; do not invent a 5th color
set. Confirm the resulting four token colors clear 3:1 (WCAG non-text UI-component threshold)
against the panel/bg gradient the gauge renders on via the same contrast tool.

## Mobile Stacked-Card Pattern (D-01) — NEW section for this phase

**Applies to:** `dashboard.html` (Scan History), `org_admin.html` (Members, Pending Invitations,
Verified Domains, Scan History — 4 tables), `api_tokens.html` (Tokens), `assets.html` (Assets
list), `asset_detail.html` (Scan History), `org_verify_domain.html` (Domains). Six templates, ~9
tables total.

**Does NOT apply to:** `scan_report.html`'s 20+ diagnostic tables (Pattern 3 in 07-RESEARCH.md —
these stay `.table-scroll` + gain `<thead>`/`<tbody>`, audited individually per-table for whether
any genuinely needs card treatment; the Findings section already renders as `.finding` cards, not
a table, and is unaffected). Do not blanket-convert every `scan_report.html` table.

### Breakpoint and mechanism

- Below `--bp-card` (430px, see Breakpoints above): the `<table>` is `display: none`, a new
  `.mobile-record-cards` list is `display: flex; flex-direction: column`.
- At and above `--bp-card`: the reverse — table shown, card list hidden.
- Both markup blocks render server-side in the same Jinja response (dual-markup, per
  07-RESEARCH.md Pattern 1) — a pure CSS `display` swap decides which is visible; no client-side
  JS/hydration.
- Both blocks share the exact same empty-state branch (`{% if scans %}...{% else %}<div
  class="empty-state">...{% endif %}`) — do not duplicate the empty-state markup once per block;
  wrap both the table and the card list in one shared conditional.

### Card anatomy (every mobile record-card follows this exact structure)

```
.card.record-card
├─ .record-card-top (flex row, justify-content: space-between, align-items: center)
│   ├─ Primary identifier/title  — <code> for URLs/hostnames/emails (matches existing
│   │                               `.target-row code` / `td.token-name` treatment, unchanged)
│   │                             — plain text for names (member name, domain name, token name)
│   └─ Severity/status indicator — reuse `.status-pill`/`.pill` exactly as the table cell does
│                                   (no new badge shape for mobile)
├─ .record-card-meta (font-size: Small token — 13px/400, color: var(--muted))
│   └─ 1-2 line summary of the "most important metadata" + "key value" —
│      e.g. "82 / 100 · Aug 18, 2026" (score + date), or "Admin · joined Aug 12" (role + date),
│      joined with " · " matching the existing `&middot;` separator convention already used
│      elsewhere in these templates
├─ [optional] .record-card-details (progressive disclosure — only when genuinely useful, per D-01)
│   └─ Implemented as a native <details><summary>Details</summary>...</details> element —
│      NOT a custom JS toggle. Native <details> is keyboard-operable and has an implicit
│      accessible name/state for free, matching the "don't hand-roll" principle in
│      07-RESEARCH.md. Only add this block where a table row actually has secondary columns
│      worth surfacing (e.g. org-admin's Members table: email as secondary detail under the
│      primary name+role card face) — omit entirely for 2-3-column tables where nothing is
│      left to disclose.
└─ .record-card-action (primary action button/link, full width)
    └─ `.btn.secondary.block` for non-destructive navigation ("View →" style, reusing the
       existing `.btn.block` modifier from 06-UI-SPEC.md's Component Canon)
    └─ `.btn.destructive.block` for a destructive action (revoke/delete), wrapped in the
       SAME <form method="POST"> + confirm() pattern as the desktop row — never simplified
```

### Touch targets

- Every tappable element inside a mobile card (the action button, any `<details><summary>`
  disclosure toggle, any icon-only control) must clear **44×44px minimum** — reuse the existing
  `.icon-btn` class verbatim (`min-width: 44px; min-height: 44px; padding: 0;`, verified
  `templates/asset_detail.html:43`) for any icon-only mobile-card action.
- **Do not** reuse `org_admin.html`'s compact `.verify-btn`/`.revoke-btn` treatment (13px
  font / 6px-12px padding, well under 44px) inside a mobile card — that treatment is a desktop-table
  inline-action convention only, explicitly called out as an anti-pattern in 07-RESEARCH.md.
- `.btn.block` (full-width) already gives the primary card action a comfortably large tap area
  without a new size token — the existing `.btn` padding (`11px 20px`) plus `width:100%` clears
  44px height on its own.

### Truncation / wrap rules

- Long identifiers (URLs, hostnames, emails) in the card's primary-identifier position: reuse the
  exact `overflow:hidden; text-overflow:ellipsis; white-space:nowrap` OR `word-break:break-word`
  treatment the corresponding table cell already uses (per 06-UI-SPEC.md's "long-text" UI
  Consideration row — already covered, don't invent a new truncation rule) — apply whichever of
  the two the source table currently uses, do not standardize on a third option.
- Card width is the full card column width (matches `.card`'s existing responsive full-bleed
  behavior inside `.wrap`) — no fixed pixel width that could itself cause overflow at 320px.

### Priority order (per D-01, restated as an implementation checklist)

1. **Understand** — primary identifier + severity/status visible with zero interaction (card face).
2. **Act** — the one primary action reachable with zero scrolling inside the card, ≥44px target.
3. **View details** — secondary columns behind a native `<details>` disclosure, not on the card
   face by default.

### `<thead>`/`<tbody>` retrofit (bundled into every table this phase touches)

Every `<table>` in scope currently renders as bare `<table><tr><th>...` with no `<thead>`/`<tbody>`
wrapper (verified: 20+ occurrences across `dashboard.html`/`org_admin.html`/`api_tokens.html`/
`assets.html`/`asset_detail.html`/`org_verify_domain.html`/`scan_report.html`, zero
`<thead>`/`<tbody>` hits). Add both wrappers to every table this phase touches (whether it gets
card treatment or stays `.table-scroll`) — purely additive, does not change `base.html`'s `table,
th, td {}` selector matching, and materially improves screen-reader table navigation. Bundle into
whichever task already touches that table's markup; do not open a separate pass for this alone.

### Claude's Discretion — concrete fix for "product name correctly positioned relative to the form"

07-RESEARCH.md's Open Question 1 flags this as unresolved without a live screenshot. Per the
`--auto` mode instruction, applying best-informed default given the existing markup (verified
`templates/base.html:231-256`, `templates/_auth_form_styles.html:15`):

**Diagnosis from static markup:** At ≤640px, `base.html`'s `.topnav` already stacks
brand-then-nav-links vertically (`flex-direction: column`) with `margin-top: 6px` between them.
Below that, `.auth-wrap` starts a *second* `padding-top: var(--space-7)` (48px) before the card
even begins. On a short viewport (iPhone SE-class, 667px tall), this produces three stacked
elements before any form field is visible: brand link → nav-links row (Login/Sign up links,
redundant with the page's own H1 or in-card swap link) → 48px gap → card. That's the "cramped,
badly positioned" symptom RESP-02 is naming — not the brand's own size or icon, but the
accumulated vertical space and redundant CTA competing with the form for the fold.

**Fix directive (uses only existing tokens, no new spacing/color/size value):**
1. On the five `.auth-wrap` pages specifically, tighten `.auth-wrap`'s top padding at narrow
   widths: add `@media (max-width: 640px) { .auth-wrap { padding-top: var(--space-5); } }` (24px
   instead of 48px) — reuses an existing spacing token, doesn't invent a new one, and directly
   shortens the brand-to-card gap on short mobile viewports.
2. On the same five pages at ≤640px, suppress the redundant topnav CTA link that duplicates the
   in-card swap link (e.g. hide `.topnav .nav-links a.cta-link` when the current page is
   `login`/`signup` and an equivalent `.swap` link already exists in the card) — implemented as a
   page-scoped conditional class or a `@media (max-width:640px)` rule scoped to `.auth-wrap`'s
   sibling `.topnav`, not a change to `.topnav`'s desktop behavior. This removes the duplicate
   "Sign up" / "Login" CTA competing with the form, without touching the nav's app-wide markup for
   authenticated pages.
3. Do not resize the brand icon/text (22px icon, 16px text) — 07-RESEARCH.md found no evidence
   the brand's own size is the problem, only the accumulated spacing/redundant-CTA stack above it.

**Verification requirement (carries into planning, not resolved by this document alone):** This
fix directive is this phase's best-informed default per the `--auto` instruction — it is
explicitly NOT a substitute for the `checkpoint:human-verify` task 07-RESEARCH.md recommends
scheduling early in the phase's plan (screenshot the five auth pages at 320/375px before and after
this fix). If the live screenshot shows a different gap than diagnosed here, the planner/executor
should adjust the fix within the same token constraints (existing `--space-*` values only) rather
than treating this diagnosis as final.

## Focus-Visible States (A11Y-03) — NEW section for this phase

**Global rule — already correct, reuse verbatim, do not duplicate or override per-component:**

```css
/* Source: templates/base.html:68 — existing, unchanged */
:focus-visible { outline: 2px solid var(--ring); outline-offset: 2px; border-radius: 4px; }
```

`--ring` = `--accent` (#22c55e). This single global rule already applies to every native
`<button>`, `<a>`, `<input>`, `<select>`, `<textarea>`, and (once retrofitted per this phase)
`<details><summary>` element in the app, because none of them are re-implemented as non-native
elements (confirmed: 07-RESEARCH.md's exhaustive `onclick`/`role="button"`/`tabindex` grep found
zero clickable-`<div>` violations across all templates).

**Per-element-type application (no new CSS, confirmation checklist only):**

| Element type | Focus treatment | Action this phase |
|---|---|---|
| `.btn` (all variants: primary/secondary/ghost/destructive) | Global `:focus-visible` ring, 2px solid `var(--accent)`, 2px offset, 4px corner radius | Confirm ring is visible against each `.btn` variant's own background during keyboard walkthrough — no CSS change expected |

**Status:** Existing coverage is already good — 07-RESEARCH.md's ripgrep audit found labels

```html

```

```javascript
// Source: templates/login.html — verified, existing, dynamic state-dependent label
document.querySelectorAll('.pw-toggle').forEach(function (btn) {
  btn.addEventListener('click', function () {
    var input = document.getElementById(btn.dataset.toggleFor);
    var showing = input.type === 'text';
    input.type = showing ? 'password' : 'text';
    btn.setAttribute('aria-label', showing ? 'Show password' : 'Hide password');
  });
});
```

**Rule for every new icon-only mobile-card action this phase adds:** `aria-label="<verb> <specific
target>"`, Jinja-interpolated with the record's own identifying name/value (never a generic "Edit"
or "Delete" with no target named) — e.g. `aria-label="Revoke {{ token.name }}"`, `aria-label="View
details for {{ member.email }}"`. The icon itself always carries `aria-hidden="true"` (matches
every existing usage) so screen readers read only the `aria-label`, not a doubled icon-name +
label announcement.

**Form-label audit (A11Y-01's other half):** No known gaps per 07-RESEARCH.md's audit — confirm
