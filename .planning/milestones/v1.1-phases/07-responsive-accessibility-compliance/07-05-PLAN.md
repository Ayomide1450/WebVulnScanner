<objective>
Give every table on the scan-report surface correct table semantics for assistive technology, audit
each one individually at 320px rather than assuming, and bring `_gauge.html`'s four hardcoded stroke
colours into the token system.

Purpose: `scan_report.html` is architecturally unlike the six record-list templates D-01 targets. It
holds 23 separate tables - 1 to 7 narrow columns each of raw check output, almost all collapsed
inside `<details>` accordions and already wrapped in `.table-scroll` - and its Findings section, the
part a user actually reads first, already renders as `.finding` cards rather than a table. Blanket
card conversion here would destroy the at-a-glance tabular comparison a security engineer wants from,
say, the headers-grade table. So this page gets the zero-risk half of the retrofit
(`<thead>`/`<tbody>`, which materially improves screen-reader table navigation and changes nothing
visually) plus the per-table 320px audit that D-01's own "audit whether such a table exists, don't
assume one does" instruction demands. `_gauge.html` comes along because it is the one file Phase 6's
token consolidation missed entirely, and because the report page is where its gauge is most
prominent.

Output: 23 tables with correct `<tbody>` (and `<thead>` on the 21 that have a column-header row,
`scope="row"` on the two that do not); a documented per-table 320px audit result; a token-based gauge
with a tool-confirmed 3:1 non-text contrast measurement.

Implements D-01: this page is where D-01's named exception applies. Its 23 diagnostic tables keep
.table-scroll rather than becoming cards, decided by a per-table audit rather than by assumption -
which is exactly what D-01 asks for when it says to audit whether such a table actually exists.
</objective>
