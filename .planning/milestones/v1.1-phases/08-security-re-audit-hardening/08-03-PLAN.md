<objective>
Close SEC-09: prove the billing ROUTES reject cross-org access, replay, and value tampering - not
just that `billing.py`'s internals do.

08-RESEARCH.md found `billing.py` well covered at the unit level (`tests/test_billing.py` proves
offset-collision-retry exhaustion and the `matched_tx_hash` double-match rejection) while
`tests/test_billing_routes.py` is 58 lines and 2 tests, both of which only assert that a pending
invoice renders as a card. There is no route-level proof that an org admin cannot verify another
org's invoice, and no proof that POSTing verify twice on a PAID invoice does not re-activate a
subscription. That is the highest-value untested surface in the app after authorization itself,
because a hit here is direct financial impact - which is exactly why D-04 sequences it second.

Purpose: the route layer is where a session identity meets an integer invoice ID. `billing.py` never
sees `current_user`; only `billing_routes.py` can get that check wrong.
Output: an extended `tests/test_billing_routes.py` carrying cross-org, replay, tampering, role-split
and listing-scope coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ORG_ADMIN session -> `/account/billing/invoice/<int:invoice_id>/verify` | An integer ID crossing into a route whose success path calls `_activate_subscription`, which writes `Organization.plan` - the value `entitlements.effective_tier()` reads to decide which intrusive checks a scan may run. A cross-org hit here is both a financial and an entitlement escalation. |
| browser form fields -> `create_invoice` | Three user-supplied values (`target_plan`, `token_symbol`, `billing_cycle`) reach pricing logic. The org id deliberately does not - it comes from the session. |
| the app -> Polygonscan's `tokentx` API | An external, untrusted response drives the paid/unpaid decision. Out of this plan's scope to redesign (`billing.py` is frozen), but every test here must stub it rather than depend on it. |
| repeated POST of the same verify action | The replay boundary. The route flashes success on a `True` return, so a user or a script can press it arbitrarily often; safety comes entirely from the PAID short-circuit. |
