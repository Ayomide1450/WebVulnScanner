<objective>
Close SEC-02: prove the app actually rejects a forged cross-site POST, rather than merely rendering
a CSRF token into its forms.

08-RESEARCH.md found the mechanism correct and app-wide - a single `CSRFProtect()` in
`extensions.py:19`, wired at `__init__.py:98`, with one deliberate `csrf.exempt(api)` for the
Bearer-token surface. What it also found is that no test in the 646-test suite has ever exercised
the enforcement path: `TestConfig` sets `WTF_CSRF_ENABLED = False`, so every CSRF-adjacent test in
the repo today asserts only that a hidden field appears in rendered markup. That is the same class
of blind spot the `RATELIMIT_ENABLED`-re-enabled test already closed for rate limiting, and it gets
the same treatment here.

Purpose: SEC-02 shares wave 1 with SEC-01 per D-04 - a CSRF hole is an authorization bypass reachable
from any page on the internet, without the attacker needing an account at all.
Output: `tests/test_csrf_enforcement.py` (new) - the first executable proof in this repo that
CSRF validation runs.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any third-party web page -> a logged-in user's browser -> this app's cookie-authenticated POST routes | The CSRF boundary proper. The attacker needs no account and no network position - only that a victim with a live session visits a page they control. |
| Bearer-token client -> `/api/v1/*` | Deliberately outside the CSRF boundary: token auth is not ambient credential auth, so a cross-site request cannot carry the token. The risk is not that this is exempt, but that the exemption is wider than intended. |
| WTForms-rendered auth forms vs. hand-written hidden inputs | Two token-emission idioms across 15 POST-form templates. A template that emits neither would be a hole invisible to a single-pattern audit. |
