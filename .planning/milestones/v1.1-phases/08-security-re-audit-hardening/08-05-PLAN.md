<objective>
Close SEC-04, SEC-05 and SEC-06 together: escaping, SQL parameterization, and file-path containment.

08-RESEARCH.md verified all three this session and found the codebase already correct on the first
two - zero unsafe-filter usages in `templates/`, zero markup-construction calls in `webvulnscanner/`,
and only two non-builder DB calls (a static healthcheck string and a parameterized Core update). So
SEC-04 and SEC-05 need proof and a standing lock, not a fix.

SEC-06 is different in kind. No route accepts a filesystem path from the user, and `Report.json_path`
is written only by `scan_engine.save_report()` from a server-generated timestamped filename - so
traversal is not reachable today. But three separate call sites (`scan_routes.py:1077`,
`api_routes.py:204`, `asset_routes.py:298`) each independently do
`open(os.path.join(REPORTS_DIR, s.report.json_path))` with no containment check, and the requirement
says these routes must be *confirmed* to be unable to serve a file outside their intended directory.
Three copies of an unguarded join is exactly the shape that becomes a real vulnerability the day
someone adds a fourth caller with a different provenance. This plan collapses them into one guarded
reader.

Purpose: SEC-04/05/06 are a single audit sweep in practice - they share one test module and one
question ("can untrusted content escape its intended representation?").
Output: `scan_engine.read_report_file()` (new, containment-checked), three call sites converted, and
`tests/test_injection_and_traversal.py` carrying the escaping, SQL and traversal locks.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scanned site's HTTP response -> `Finding.title` / `Finding.detail` -> `scan_report.html` | The primary stored-XSS path.
