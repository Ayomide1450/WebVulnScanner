<objective>
Close the phase: fire real HTTP requests at a real running instance to confirm the boundaries the
first six plans proved through the test client, then gate the phase on recorded evidence per
requirement rather than on a green suite.

CONTEXT.md D-01 asks for this deliberately. Flask's test client shares a process, a session interface
and an import graph with the app under test; it short-circuits the WSGI layer, real cookie handling
and real Origin/Referer processing. Those are exactly the layers a cross-origin CSRF attempt and a
raw cross-org request actually traverse. D-02 bounds it: the probe is a verification step, never a
replacement - every case it covers already has a test-client regression test from plans 08-01 through
08-06.

The second half of this plan exists because Phase 7 closed with eight requirements code-complete and
unconfirmed, their human-verify gates never answered and their evidence never recorded. The evidence
gate below is the mechanism that prevents Phase 8 repeating it.

Purpose: turn a suite of green tests into a phase whose ten requirements each have a named,
recorded observation behind them.
Output: `scripts/live_probe_phase8.py`, `tests/test_live_probe_script.py`, a recorded probe result,
and the phase evidence gate discharged.
</objective>

    exercises the real WSGI stack, real cookie handling and real Origin/Referer processing that the
    test client short-circuits.

    not submit a scan against any third-party target - the distinction CONTEXT.md D-01 draws
    explicitly against CLAUDE.md's authorized-use constraint.

  <how-to-verify>
    From the repo root, in a shell where the venv is active:

    1. Create the disposable environment and seed it:
       `set FLASK_SKIP_DOTENV=1`
       `set SESSION_COOKIE_SECURE=false`
       `set ALLOW_INSECURE_DEV_SECRET_KEY=true`
       `.venv\Scripts\python scripts\live_probe_phase8.py --seed`
       This creates a throwaway SQLite file, prints its path, and prints the seeded org/user/object
       ids. Confirm the printed path is a temporary file and NOT `glassbox.db`. If it is not,
       stop - the guardrail failed and that is itself a finding.

    2. In a second shell with the same three env vars set, start the app against that same disposable
       database (the script prints the exact command to use, including the
       `SQLALCHEMY_DATABASE_URI` value):
       `.venv\Scripts\python app.py`
       Confirm it starts on `http://127.0.0.1:5000` and that `http://127.0.0.1:5000/healthz` returns
       ok.

       `.venv\Scripts\python scripts\live_probe_phase8.py --probe --base-url http://127.0.0.1:5000`

    4. Read the printed per-case table. For each case it reports:
       - the case name and route
       - the expected outcome (403, 404, 400, or a specific refusal)
       - the observed status code
       - pass or fail
       - the named regression test covering the same case

    5. Report back:
       - the script's exit code (0 means every case behaved as expected)
       - the full per-case table, pasted
       - any case marked FAIL, with its route and observed status
       - whether the foreign-`Origin` CSRF case was refused
       - confirmation that step 1's printed database path was a temporary file

    6. Stop the app and delete the disposable database file.

    If any case FAILS, that is a live finding. Per D-03 it gets fixed immediately within this phase,
    and per D-02 it also gets a Flask-test-client regression test so the guarantee survives without a
    live server. Report the failure rather than working around it.
